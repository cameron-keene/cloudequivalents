Microsoft Ignite ran this week and AWS kept up its run of pre-re:Invent launches, so both feeds were long. Most of it was single-cloud detail. This post sticks to the changes that move how the three clouds line up: Azure now has a GA answer to Aurora PostgreSQL, AWS and Azure each shipped managed private links to the other cloud, Cosmos DB and DynamoDB both got better vaulted backups, and Azure Spot VMs gained a tier that warns you about as early as EC2 Spot does. Two follow-ups to last week's edge story, certifications, and retirements are at the end.

## Azure HorizonDB is generally available

On Nov 17, Microsoft announced [Azure HorizonDB as generally available](https://azure.microsoft.com/updates?id=579388). It's a PostgreSQL service with stateless compute and a shared storage layer. The [overview](https://learn.microsoft.com/en-us/azure/horizondb/overview) describes a database-as-a-log design: compute writes only WAL to storage, with separate WAL and data storage fleets, zone-resilient storage by default, and storage that grows on its own. A cluster has one writer and up to 15 reader nodes that all share one copy of the data, so adding a reader doesn't copy data.

Around the GA, Microsoft also shipped [geo-redundant backup and restore](https://azure.microsoft.com/updates?id=574168), and put two migration paths into Azure Database Migration Service in preview: [from Azure Database for PostgreSQL flexible server](https://azure.microsoft.com/updates?id=579612) and [from Oracle](https://azure.microsoft.com/updates?id=579226) (data only, after you convert the schema yourself).

The GA overview also lists what isn't there yet. That list matters more than the launch post if you're coming from Aurora or AlloyDB:

| | Amazon Aurora PostgreSQL | Azure HorizonDB (GA) | AlloyDB for PostgreSQL |
|---|---|---|---|
| Readers sharing storage | Up to 15 [Aurora Replicas](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Replication.html) | Up to 15 reader nodes. Only one compute pool per cluster for now (separate read pools aren't available) | [Read pool instances](https://docs.cloud.google.com/alloydb/docs/overview) |
| Readers in another region | [Aurora Global Database](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html) | Not available. For DR, use geo-redundant backup and restore to the paired region | [Cross-region secondary clusters](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication) |
| Managed connection pooling | [RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/rds-proxy.html) | Not available. Use an external pooler | Not covered here |
| Backup retention | [1 to 35 days](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Backups.html) | Up to 35 days, with no long-term retention | Not covered here |
| Other gaps Microsoft lists | | No in-place major version upgrade, no VNet injection (Private Link only), customer-managed keys and geo-redundant backup can't be combined, system-managed maintenance windows only | |

What it means for the mappings: on [Aurora PostgreSQL vs Azure HorizonDB](/compare/aws-aurora-postgresql-vs-azure-horizondb/), the main caveat was that HorizonDB was preview and flexible server was the production answer. That's gone. HorizonDB is now the like-for-like target for Aurora PostgreSQL's architecture, and the differences are about features: no cross-region readers and no built-in pooler. If you rely on Global Database or RDS Proxy today, flexible server isn't the fallback either, so plan for app-side pooling and a backup-based regional DR story. The Google Cloud mapping, [Aurora PostgreSQL vs AlloyDB](/compare/aws-aurora-postgresql-vs-gcp-alloydb/), doesn't change. For AZ-305 study, expect "cloud-native PostgreSQL with shared storage" to have a GA Azure answer now.

## The clouds now connect to each other as managed services

Three things shipped on Nov 17 that make "AWS plus Azure" or "AWS plus Google Cloud" something the providers run for you, not something you assemble:

- **Network.** [AWS Interconnect - multicloud with Microsoft Azure is GA](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-announces-AWS-interconnect-multicloud-azure-ga/) in us-east-1, ap-southeast-2 and eu-central-1. On the same day, Microsoft announced [Azure Multicloud Interconnect](https://azure.microsoft.com/updates?id=579766) as GA, with AWS generally available and Google Cloud in public preview. Each side has its own resource, and an activation key pairs them. AWS [describes](https://docs.aws.amazon.com/interconnect/latest/userguide/what-is-interconnect.html) redundant devices in at least two facilities and no routers, cross-connects or BGP sessions for you to manage. Microsoft's [overview](https://learn.microsoft.com/en-us/azure/multicloud-interconnect/overview) says it's built on ExpressRoute (you create an ExpressRoute circuit with the Multicloud Interconnect port type), with MACsec on by default on the physical links. Google Cloud's version of the same idea is [Partner Cross-Cloud Interconnect for AWS](https://docs.cloud.google.com/network-connectivity/docs/interconnect/concepts/partner-cci-for-aws-overview), an on-demand, provider-managed AWS link that you attach through Network Connectivity Center or VPC Network Peering.
- **Security posture.** [AWS Security Hub now monitors Google Cloud](https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-gcp/) VMs, Artifact Registry images, Cloud Run functions and identities, with CIS Google Cloud checks. It already covered Azure. Defender for Cloud already connects to [AWS](https://learn.microsoft.com/en-us/azure/defender-for-cloud/quickstart-onboard-aws) and [Google Cloud](https://learn.microsoft.com/en-us/azure/defender-for-cloud/quickstart-onboard-gcp), and Security Command Center connects to [AWS](https://docs.cloud.google.com/security-command-center/docs/connect-scc-to-aws) (on the Enterprise tier, which Google is shutting down on May 21, 2027).
- **Operations.** [CloudWatch Omni now collects Azure telemetry](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudwatch-omni-microsoft-azure) (Nov 21): resource logs, Azure Monitor platform metrics, VNet flow logs, and Application Insights traces, after you connect an Entra ID tenant. Going the other way, [Azure SRE Agent now has AWS and Google Cloud connectors](https://azure.microsoft.com/updates?id=580975) in preview. They use federation to an AWS IAM role and Google Cloud Workload Identity Federation, with no stored access keys.

What it means for the mappings: our [Direct Connect vs ExpressRoute](/compare/aws-direct-connect-vs-azure-expressroute/) and [Direct Connect vs Cloud Interconnect](/compare/aws-direct-connect-vs-gcp-cloud-interconnect/) pages are about reaching the cloud from your own sites. Cloud-to-cloud links are now their own product on all three providers, and AWS Interconnect - multicloud, Azure Multicloud Interconnect and Partner Cross-Cloud Interconnect line up closely enough to deserve their own row. For [Security Hub vs Defender CSPM](/compare/aws-security-hub-cspm-vs-azure-defender-cspm/), "which other clouds does it cover" is no longer a point in Azure's favor. On the cert side, ANS-C01 and AZ-700 candidates should keep the two apart: the multicloud products link one cloud to another, and Direct Connect and ExpressRoute remain the answer for your own data centers. (AWS Interconnect also has a separate last-mile offering for branch sites through partner networks.)

## Vaulted, incremental NoSQL backups on AWS and Azure

The same week, both providers improved how their central backup service protects their main NoSQL database:

- **Azure Backup for Azure Cosmos DB is GA** ([announcement](https://azure.microsoft.com/updates?id=579147)). It stores immutable copies in a Backup vault outside the Cosmos DB account, with retention of up to 10 years. A weekly full plus daily incrementals gives a 1-day RPO, and you can restore across subscriptions or to the paired region. It's for NoSQL and RU-based MongoDB accounts that already use continuous backup. The [overview](https://learn.microsoft.com/en-us/azure/backup/backup-azure-cosmos-db-overview) positions it on top of Cosmos DB's native backups, which keep up to 35 days.
- **AWS Backup now takes incremental DynamoDB backups** ([announcement](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-backup-incremental-backups-dynamodb/)). After an initial full copy, each backup holds only changes, with a new full every 15 days. Schedules can run hourly to weekly, and backups can go into logically air-gapped vaults. Cross-Region copies are incremental too. It's on by default for new AWS Backup DynamoDB customers, and existing customers opt in under advanced settings. Native [point-in-time recovery](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Point-in-time-recovery.html) still covers up to 35 days.
- **Google Cloud:** Firestore has its own [scheduled backups](https://docs.cloud.google.com/firestore/native/docs/backups) (daily or weekly, stored in the same location as the database, restored to a new database), configured in Firestore itself.

What it means for the mappings: [AWS Backup vs Azure Backup](/compare/aws-backup-vs-azure-backup/) currently says Cosmos DB relies on its own built-in backups. That's now wrong, and both sides cover their flagship NoSQL store in a central, immutable vault. The two-layer pattern (native PITR for about 35 days, then a central vault for long-term and ransomware recovery) is now the same on AWS and Azure. That's a useful thing to remember for [DynamoDB vs Cosmos DB](/compare/aws-dynamodb-vs-azure-cosmos-db-nosql/) migrations and for AZ-104 and SAA-C03 backup questions.

## Azure Spot plus narrows the gap with EC2 Spot

The biggest practical difference on [EC2 Spot vs Azure Spot VMs](/compare/aws-ec2-spot-vs-azure-spot-vms/) has been the warning time. [Azure Compute Spot plus](https://azure.microsoft.com/updates?id=581145), in public preview, is a higher-priced Spot tier aimed at that gap. Microsoft's [blog post](https://techcommunity.microsoft.com/blog/azurecompute/public-preview-azure-compute--spot-plus/4573059) lays out the differences:

| | EC2 Spot | Azure Spot | Azure Spot plus (preview) | Google Cloud Spot VMs |
|---|---|---|---|---|
| Final warning | [Two minutes](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-instance-termination-notices.html) (none if hibernating) | Up to 30 seconds | 30 seconds to 2 minutes | [Preemption notice](https://docs.cloud.google.com/compute/docs/instances/spot) of 0 (default) or 120 seconds, then a best-effort shutdown of up to 30 seconds |
| Early risk signal | [Rebalance recommendation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/rebalance-recommendations.html) | Rebalance notification, up to 15 minutes | Rebalance notification, typically 30 seconds to 15 minutes | Not covered here |
| Runtime promise | None | None | Targets at least 60 minutes (best effort), with no charge if evicted inside the first 60 minutes | None |
| Price | Spot price | Up to 90% off pay-as-you-go | Above Spot, below pay-as-you-go | Spot price |

So the "two minutes vs 30 seconds" line many of us memorized for SAA-C03 and AZ-104 now needs an asterisk: on Azure it depends on which Spot tier you pick. The 60-minute billing protection has no direct EC2 or Compute Engine counterpart in the pages we checked. The [Google Cloud mapping](/compare/aws-ec2-spot-vs-gcp-spot-vms/) doesn't change.

## Follow-ups: edge code and JWT checks

Last week we compared Azure Front Door's new edge actions with CloudFront Functions. Two AWS changes this week shift that comparison:

- **CloudFront Functions can now make network calls** ([announcement](https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-functions-network-calls/), Nov 18). `cf.fetch()` calls an origin that's already configured on the distribution, and `cf.beacon()` sends events in the background. The [developer guide](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/helper-functions-network-calls.html) says it requires JavaScript runtime 2.0, takes an origin ID rather than an arbitrary host name, and times out after 1 second. It's billed per call on top of invocations. Calling another service used to be one of the reasons to pick Lambda@Edge. We didn't find outbound calls described in the [edge actions documentation](https://learn.microsoft.com/en-us/azure/frontdoor/edge-actions), so the lightweight tiers on AWS and Azure have moved further apart.
- **API Gateway REST APIs now have a native JWT authorizer** ([announcement](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-api-gateway-rest-authorizers-jwt/), Nov 17). [HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html) already had one. REST APIs needed a Lambda authorizer for tokens from any issuer other than Cognito. That's the same configure-don't-code model as API Management's [validate-jwt policy](https://learn.microsoft.com/en-us/azure/api-management/validate-jwt-policy) and Google Cloud API Gateway's [JWT authentication](https://docs.cloud.google.com/api-gateway/docs/authenticating-users-jwt).

Affected pages: [CloudFront Functions vs Front Door rules engine](/compare/aws-cloudfront-functions-vs-azure-front-door-rules-engine/), [Lambda@Edge on Azure](/compare/aws-lambda-at-edge-vs-azure/), and [API Gateway vs API Management](/compare/aws-api-gateway-vs-azure-api-management/).

## Retirements and smaller changes

- **Azure AI Gateway is now its own GA service** ([announcement](https://azure.microsoft.com/updates?id=580080)). It used to be the AI Gateway tier of API Management. It sits in front of models and MCP tools from multiple providers, with routing, failover, token budgets and quotas, and usage-based pricing after 10,000 free requests per subscription per month. Our API Management mapping still describes AI gateway as an API Management feature.
- **Key Vault Premium symmetric keys are GA** ([announcement](https://azure.microsoft.com/updates?id=579374)). HSM-backed AES keys (oct-HSM, 128, 192 or 256 bits), which Managed HSM already supports, moved from a July preview to production support in Premium vaults ([key types](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys)). That brings ordinary (Premium) vaults closer to how most people use AWS KMS symmetric keys ([KMS vs Key Vault](/compare/aws-kms-vs-azure-key-vault/)). Separately, [KMS keys can now be shared through AWS RAM](https://aws.amazon.com/about-aws/whats-new/2026/11/kms-key-sharing-resource-access-manager/) with reusable managed permissions, instead of you editing key policies by hand.
- **The Azure Functions OpenAI extension loses support on April 20, 2027** ([notice](https://azure.microsoft.com/updates?id=579952)). Microsoft says to call the OpenAI, Microsoft Foundry or Azure AI Search SDKs directly.
- **Azure Cache for Redis to Azure Managed Redis migration tooling is GA** ([announcement](https://azure.microsoft.com/updates?id=577579)). It redirects the existing cache host name to an Azure Managed Redis instance, so clients reconnect with the same host name and access key. If you're mapping ElastiCache to Azure, [ElastiCache vs Azure Managed Redis](/compare/aws-elasticache-vs-azure-managed-redis/) is still the right target, and this makes moving off the retiring service easier.
